# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal
Deliver the MVP Requester-facing ticketing experience for TokTickIT under the Zen Green design language, enabling simulated Requesters to create tickets, view/filter their tickets, inspect details, and manage attachments with soft removal.

## 2. Stakeholder Request Interpretation
The IT department requires an end-user support ticketing workflow. Requesters must describe issues, select categories/systems, set requested priority, and upload evidence. Because real authentication is scheduled for Lab 3, a temporary Development Requester selection mechanism must be provided for testing and multi-user isolation.

## 3. Scope
### Included
- Development Requester selector (testing context)
- Create Ticket workflow with frontend/backend validation
- My Tickets list with search, filter, sort, and pagination
- Ticket Detail view (Read-only) with attachment upload, download, and soft-removal
- Cross-requester data isolation
- Zen Green UI theme and responsive layouts

### Excluded
- Real user authentication (login/logout, passwords, sessions, JWT)
- IT Staff queues, ticket claiming, reassignments, or changing IT priority
- Collaboration (Public comments, Internal notes, Service actions)
- Ticket lifecycle status transitions beyond "New"
- System administration

## 4. Functional Requirements
- **FR-01**: The system shall provide a Development Requester selector to set active user context from database records.
- **FR-02**: A Requester shall create support tickets by providing Category, Related System, Requested Priority, Summary, and Description.
- **FR-03**: The system shall generate a unique official Ticket Number upon creation.
- **FR-04**: A Requester shall view a paginated list of their own tickets in "My Tickets".
- **FR-05**: The system shall allow searching tickets by Ticket Number or Summary, and filtering by Category, Priority, and Status.
- **FR-06**: A Requester shall view details of their owned ticket in read-only mode.
- **FR-07**: A Requester shall upload permitted attachments (JPG, PNG, WEBP, PDF <= 5MB) up to 5 active files per ticket.
- **FR-08**: A Requester shall soft-remove an attachment with a mandatory reason.
- **FR-09**: The system shall reject any attempt by Requester A to access or modify tickets/attachments belonging to Requester B.

## 5. Business Rules
- **BR-01**: The official Ticket Number is generated by backend (Format: `TKT-YYYY-XXXXXX`) and must be globally unique.
- **BR-02**: A new ticket must initialize with `Current Status = New`.
- **BR-03**: Lab 2 uses a Development Requester selector instead of login; this is strictly a testing mechanism.
- **BR-04**: Inactive Requesters must not appear in the selector and cannot create tickets.
- **BR-05**: Allowed attachment file types are JPG, JPEG, PNG, WEBP, and PDF. Maximum size is 5 MB per file.
- **BR-06**: Maximum active attachments per ticket is 5.
- **BR-07**: Attachment removal must be implemented as soft-removal (`isDeleted = true`). Removed files cannot be downloaded or previewed, but metadata remains visible.
- **BR-08**: Form values must be preserved when submission fails or backend errors occur.

## 6. UI Specification Summary
Adheres to the Zen Green design system with standard form inputs, responsive tables/cards, badges for statuses and priorities, accessible focus states, and specific viewport layouts (Desktop >= 992px, Tablet 768-991px, Mobile < 768px). Full details in `ui-spec.md`.

## 7. Data Changes
- **Models**: `RequesterUser`, `Ticket`, `Attachment`, `Category`, `RelatedSystem`
- **Relationships**:
  - Requester (1) -> Tickets (N)
  - Ticket (1) -> Attachments (N)
  - Category (1) -> Tickets (N)
  - RelatedSystem (1) -> Tickets (N)
- **Soft Delete**: `Attachment.isDeleted`, `Attachment.deletedReason`, `Attachment.deletedAt`

## 8. API Contract
Summarized endpoints (Full detail in `api-spec.md`):
- `GET /api/requesters/active`
- `GET /api/categories` & `GET /api/related-systems`
- `POST /api/tickets`
- `GET /api/tickets` (with query params)
- `GET /api/tickets/:id`
- `POST /api/tickets/:id/attachments`
- `DELETE /api/attachments/:id`

## 9. Acceptance Criteria
- **AC-01**: Given valid ticket fields, when the Requester submits, then a ticket is created with status "New" and a unique Ticket Number is returned.
- **AC-02**: Given no Development Requester is selected, when opening ticket screens, then the user is redirected to the Requester Selection screen.
- **AC-03**: Given Requester A is selected, when attempting to fetch or mutate tickets of Requester B, then the backend rejects the request (403 Forbidden / 404 Not Found).
- **AC-04**: Given an attachment file > 5MB or invalid type, when uploading, then the system rejects it with an explicit validation error.
- **AC-05**: Given an active attachment, when soft-removed with a reason, then it becomes non-downloadable and its metadata reflects the removed state.
- **AC-06**: Given keyword search and filters in My Tickets, when applied, then only matching tickets owned by the current requester are returned with pagination metadata.
